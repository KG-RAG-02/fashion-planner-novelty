# 0004 · 순차 이미지 생성, 자동 재시도 없음, 재요청 원장

- 상태: 채택
- 범위: 상품·착장 이미지, 요청 처리

## 맥락

- 이미지 호출은 느리고 유료다.
- 독립적인 이미지 호출 두 번이 눈에 띄게 다른 옷을 만들었다. [T-IMG-01](../troubleshooting.md#t-img-01) 참고.
- 시간 초과로 끊긴 클라이언트는 제공자가 이미 요청을 처리하고 청구했는지 알 수 없다. 무작정 재시도하면 두 번 낼 수 있다.

## 결정

- **순서**: 상품 이미지를 먼저 만든다. 착장 이미지는 저장된 상품 이미지를 편집해 만들고, 사진이 있는 동반 재고 상품이 있으면 그 사진을 두 번째 입력으로 넣는다. 상품 이미지가 없으면 착장은 건너뛴다(`OUTFIT_REFERENCE_UNAVAILABLE`).
- **같은 사양**: 두 프롬프트는 같은 JSON 사양을 넣고, 그 SHA-256을 두 visual에 모두 기록한다.
- **프로세스당 이미지 한 쌍씩**: 동시에 들어온 두 번째 요청은 줄을 서지 않고 `IMAGE_CAPACITY_BUSY`를 받는다.
- **자동 재시도 없음**: 실패하거나 시간이 초과된 호출은 안전한 오류 코드로 보고한다.
- **원장**: 로컬 SQLite 원장에 다음을 기록한다.
  - 저장된 이미지(SHA-256으로 내용 주소화)가 어느 요청 것인지
  - 유료 이미지 호출 전에 잡는 실행 선점(claim)
  - 최종 응답
- **재요청 규칙**
  - 같은 request ID와 같은 페이로드는 저장된 응답을 돌려준다.
  - 같은 request ID에 다른 페이로드는 `409 REQUEST_ID_REUSED`다.
  - 선점은 있는데 저장된 응답이 없으면 `409 IMAGE_REQUEST_IN_PROGRESS_OR_OUTCOME_UNKNOWN`이다.
  - 일부러 다시 시도하려면 새 request ID를 쓴다.

## 결과

- 실제로는 두 visual이 같은 옷을 보여 주지만, 픽셀 수준의 동일성은 자동으로 검증하지 않는다.
- 이미지 단계는 호출당 시간 제한의 약 두 배까지 걸릴 수 있다.
- 선점과 응답 저장 사이에 프로세스가 죽으면 그 request ID는 막힌다. 운영자는 새 ID로 다시 시도해야 한다. 조용히 두 번 내지 않는 대가다.

## 검토한 대안

| 대안 | 택하지 않은 이유 |
|---|---|
| 텍스트→이미지 동시 호출 두 번 | 빠르지만 옷이 달랐다 |
| 백오프 자동 재시도 | 첫 호출이 성공했는데 응답만 잃은 경우 두 번 청구될 위험이 있다 |
| 이미지 요청 큐 | 단일 프로세스 서비스에 비해 움직이는 부품이 많다. 호출하는 쪽이 나중에 새 ID로 다시 시도할 수 있다 |
