# 0001 · 표준 라이브러리 코어와 생성기 포트

- 상태: 채택
- 범위: 서비스 전체

## 맥락

이 서비스를 시작할 때 모델 제공자, 서비스 간 전송 방식, 공통 계약이 모두 정해지지 않았다. 그래도 기획 로직은 먼저 만들고 검증하고 싶었다. 그 기획 로직은 다음 세 가지다.

- 입력을 추적할 수 있게 유지한다.
- 사실, 해석, 제안을 구분한다.
- 수요나 생산 가능성 판단은 다른 서비스에 맡긴다.

## 결정

- 도메인 코어는 Python 표준 라이브러리만 쓴다. 입력 확인, 기획 컨텍스트, Draft 생성, 출처 검사를 dataclass와 순수 함수로 만든다.
- 첫 생성기는 결정적인 규칙 기반 생성기다. 모델 기반 생성기는 나중에 같은 `ConceptGenerator` 포트 뒤에 붙였고, 규칙 기반 Draft가 그 대체본으로 남는다.
- 입력이 뒷받침하지 않는 값은 사실처럼 채우지 않는다. `unknown`으로 두거나, 검토 질문으로 남기거나, `proposal`로 표시한다.
- HTTP 서비스는 코어를 감싸는 얇은 어댑터(`http.server`)다. 코어는 웹 프레임워크에 의존하지 않는다.

## 결과

- 서드파티 패키지 없이 서비스가 돌고 테스트가 통과한다. `python-dotenv`는 선택 사항이다.
- 규칙 기반 Draft는 담백하고 시장성을 판단하지 않는다. 모든 모델 응답을 비교하고 실패 시 되돌아가는 검토용 기준선이다.
- `http.server`는 인터넷에 직접 노출할 만큼 단단하지 않다. 이 서비스는 사설 네트워크에서 orchestrator 뒤에 두는 것을 전제로 하며, `service` 모드는 TLS와 bearer 토큰을 더한다.

## 검토한 대안

| 대안 | 지금 택하지 않은 이유 |
|---|---|
| 처음부터 LLM 생성기 | 모델, 데이터 전송 조건, 평가 기준, 비용이 정해지지 않았다. 제약 없는 모델은 근거가 없는 세부 사항을 지어낸다 |
| wire 스키마를 먼저 고정 | 공통 계약보다 앞서 나가 통합 비용을 키운다 |
| 웹 프레임워크부터 시작 | 아직 열려 있던 전송 결정에 도메인 로직이 묶인다 |
