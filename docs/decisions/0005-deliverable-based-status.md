# 0005 · 상태는 산출물을 기준으로 하고, 세부 사항은 이슈 목록에 둔다

- 상태: 채택
- 범위: 응답의 `status`

## 맥락

실제 입력에는 거의 언제나 한계 문장이 들어 있다. 예를 들면 샘플 재고, 대체한 지난 시즌, 아직 정하지 않은 정책이다. 그중 하나만 있어도 `partial`이 되자 실데이터 실행은 모두 `partial`이었고, orchestrator는 그 상태를 기획 전체로 넘겼다. [T-STATUS-01](../troubleshooting.md#t-status-01) 참고.

## 결정

- `status`는 Draft와 이미지 두 장이 만들어지고 상위 입력이 모두 `ok`일 때 `ok`다. 그 밖에는 `partial`이다.
- 계약 오류는 HTTP 4xx로 거절하고 `partial` 결과로 만들지 않는다.
- 검토자가 볼 이유는 상태와 상관없이 `validation_issues`(기계가 읽는 코드)와 `limitations`(문장)에 모두 남긴다.

## 결과

- 이제 `ok`는 "온전한 입력으로 만든 온전한 산출물"을 뜻한다. "주의 사항 없음"이라는 뜻은 아니다.
- 세부 사항이 필요한 소비자는 `status`만 보지 말고 `validation_issues`를 읽어야 한다.

## 검토한 대안

| 대안 | 택하지 않은 이유 |
|---|---|
| 한계가 하나라도 있으면 `partial` | 실데이터에서 상태가 의미를 잃었다 |
| 상태 값을 늘림 | 모든 소비자가 새 값을 이해해야 한다. `validation_issues`의 코드가 계약을 바꾸지 않고 세부 사항을 전한다 |
