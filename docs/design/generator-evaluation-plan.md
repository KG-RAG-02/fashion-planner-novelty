# 근거 기반 상품 콘셉트 생성 및 엔진 비교 평가 계획

- 상태: 평가 설계 제안 · 미실행
- 범위: RAG 근거 준비, `ConceptGenerator` 구현체 비교, `ProductConceptDraft` 검증
- 측정 결과: 없음

이 에이전트의 목표는 상품 콘셉트를 자료에 근거해 생성하고, 복수의 생성 엔진을 재현 가능한 평가로 비교해 MD에게 더 유용한 결과를 제공하는 것입니다. 이 문서는 실행 전 평가 설계입니다. 승인된 자료로 실제 실험을 하기 전까지 품질 향상이나 우수 엔진을 주장하지 않습니다. 결과는 이 에이전트의 제안 품질만 다루며, 시장 성과나 판매 성과를 뜻하지 않습니다.

## 비교 구조

평가를 두 트랙으로 분리합니다.

1. **생성 엔진 비교:** `PlanningRequest`, `TrendResult`, `InventoryProductResult` 입력을 동일하게 제공하고 생성기만 바꿉니다. 판매·시장 분석은 P06 입력이 아니므로 비교 조건에 포함하지 않습니다. 이 비교로 프롬프트·생성 모델의 차이를 살핍니다.
2. **End-to-end RAG 비교:** 검색 설정 또는 검색 파이프라인까지 바뀌는 실험은 별도 트랙으로 기록합니다. 결과 차이를 검색 품질과 생성 품질로 나눠 해석하며, 생성 엔진 비교 결과와 합치지 않습니다.

현재 3번 에이전트는 자체 검색기나 인덱스를 소유하지 않으며, 1번 에이전트가 전달한 트렌드 Evidence를 사용합니다. 따라서 우선 생성 엔진 비교의 검색 컨텍스트는 고정합니다. 이후 여러 검색 엔진을 비교할 때는 각 검색 결과를 저장·버전 관리하고 retrieval-only 평가와 전체 파이프라인 평가를 추가합니다.

## 데이터셋과 실험 통제

- 대표 요청을 카테고리·시즌·요청 속성, 입력 상태(`ok`/`partial`/`no_results`/`error`), Evidence 충분성, 입력 간 충돌 유형별로 층화해 준비합니다.
- 입력 데이터와 Evidence는 합성 또는 사용 권한이 확인된 자료만 사용합니다. Dataset snapshot ID, 출처·라이선스 상태, 기준일, 필드 누락과 적용 범위를 기록합니다.
- 개발용 prompt 조정 자료와 최종 비교용 holdout 사례를 분리합니다. 평가 사례를 prompt 예시로 재사용하지 않습니다.
- 엔진 비교 시 동일한 입력, Evidence 순서/내용, prompt 버전, 출력 스키마, 토큰 한도와 생성 설정을 적용합니다. 제공자 간 동일하게 맞출 수 없는 설정은 차이와 이유를 기록합니다.
- 결과를 무작위 ID로 가리고, 가능한 경우 엔진 이름을 모르는 MD 평가자가 블라인드로 검토합니다. 실행 순서와 반복 횟수는 실험 전에 정하고 모든 엔진에 동일하게 적용합니다.
- 엔진별 제공자·모델·버전, API/실행 환경, prompt hash/version, decoding 설정, 코드 commit, dataset snapshot, 검색 결과 버전, 실행 시각, 재시도/실패와 비용·지연을 기록합니다. API key 및 비밀값은 절대 기록하지 않습니다.
- 모델 엔진 목록, 사용 데이터 전송 허용 범위, 비용/지연 한도는 팀 결정 전까지 미정입니다. 후보 엔진은 비교 표에서 익명 ID로 시작할 수 있습니다.

## 측정 지표 후보

각 지표를 엔진별·시나리오별로 따로 보고합니다. 팀이 가중치를 합의하기 전에는 임의의 단일 종합 점수로 순위를 정하지 않습니다.

| 차원 | 측정 방법 | 실패 신호 |
| --- | --- | --- |
| Evidence 참조 유효성 | 자동 검사: 출력이 참조한 모든 Evidence ID가 해당 입력 allowlist에 있는지 | 입력에 없는 ID, 잘못된 locator 또는 권한 불명 출처를 인용 |
| 주장 근거성 | 핵심 사실 주장별로 근거가 실제 주장을 지지하는지 사람 검토 또는 합의된 adjudication | 인용은 있으나 근거가 주장을 지지하지 않음, 근거 없는 사실 주장 |
| 주장 출처 표시 | 요청, 관찰, 해석, 제안, 가설, 미확정을 정확히 구분하는지 루브릭 평가 | 가설/제안을 확인된 고객 수요·사실처럼 서술 |
| 요청·제약 준수 | 시즌·카테고리·시장·채널·속성 및 금지 범위 자동/수동 검사 | 요청 조건 무시, 재고를 판매로 오인, 근거 없는 경쟁·원가 추정 또는 과거 판매 관찰을 미래 수요로 단정 |
| 콘셉트 유용성 | MD 블라인드 루브릭: 구체성, 일관성, 검토 가능성, 근거를 활용한 차별화 방향 | 일반론만 반복하거나 근거와 연결되지 않은 구체성 |
| 완전성·불확실성 처리 | 필수 개념 요소, 미입력 사항, 위험, 검증 질문이 알맞게 표현되는지 루브릭/구조 검사 | 임의 소재·핏·가격·고객 조건 채움, 확인 질문 누락 |
| 모순·unsupported claim 비율 | 주장 단위 검토에서 자료와 충돌하거나 뒷받침되지 않은 사실 주장의 비율 | 엔진 간 과도한 환각/모순 |
| 강건성 | `partial`, `no_results`, `error`, 상충 입력에 대한 상태 보존과 안전한 제한 동작 | 누락을 성공으로 가장하거나 0으로 치환 |
| 운영 비용/지연 | 엔진/호출별 측정값과 실패율 | 합의한 비용·지연 한도 초과(한도 합의 전에는 관찰값만 기록) |

품질 향상 판단은 한 점수만으로 내리지 않습니다. 근거성, 제약 준수, 강건성에 최소 통과선을 먼저 합의하고, 이를 통과한 후보끼리 MD 유용성 평가와 비용·지연을 함께 검토합니다. 기준선 대비 차이, 사례 수, 평가자 간 불일치와 불확실성도 함께 표시합니다.

## 시나리오와 기대 동작

| 시나리오 | 입력 조건 | 기대 동작 |
| --- | --- | --- |
| 정상 입력 | 트렌드·요청·재고가 같은 request/schema 버전이고 각 근거 ID가 유효. 판매 분석은 선택 입력 | 트렌드 근거를 먼저 검토하고 요청 범위를 확인한 뒤 자사 상품/재고를 검토한다. 선택 판매 관찰이 있으면 상태와 Evidence를 보존 |
| 동일 에이전트의 두 결과 | PlanningRequest와 TrendResult의 `agent_id`가 동일 | 허용. 두 결과의 상태는 각 입력 슬롯에 따로 보존 |
| 필수 재고 입력이 누락 | 유효한 트렌드·요청 입력, InventoryProductResult 누락 (판매 입력 유무와 무관) | 입력 오류 처리. 세 핵심 입력이 모두 도착한 것처럼 초안을 만들지 않음 |
| 재고 조회 결과는 있으나 수량 미확정 | 상품/속성 Evidence는 있으나 quantity 없음 | 상품 비교는 수행하고 재고 수량은 미확정으로 둠 |
| 트렌드 부분 결과 | `TrendResult.status=partial`, 일부 후보와 제한사항 존재 | 가진 근거는 사용하고 partial 상태·제한을 보존. 자료가 완전한 것처럼 표시하지 않음 |
| 재고 no_results | 조회 자료 없음 | 재고 0으로 만들지 않음. 상태와 조회 확인 질문을 보존 |
| 실제 재고 0 | 재고 레코드에 수량 0, 단위·정의·기준일·Evidence가 명시됨 | 실제 0 수량과 스냅샷 근거를 자사 상품 관계 메모에 보존. 수요나 판매 부진으로 해석하지 않음 |
| 조건 충돌 | 요청과 트렌드/재고 사이 시즌·지역·카테고리·속성 값이 겹치지 않음 | 충돌과 확인 질문을 기록하고 충돌을 임의로 해소한 제안을 만들지 않음 |
| 근거 없는 트렌드 속성 | 후보 속성에 Evidence ID가 없음 | 관찰로 단정하지 않고 검증 대상으로 표시 |
| 모르는 Evidence ID | draft가 입력 컨텍스트에 없는 ID를 참조 | 검증 이슈 `UNKNOWN_EVIDENCE_ID` 반환 |
| 요청에 없는 사용자 속성 | 생성 초안이 임의 값을 `user_requested`로 표시 | 검증 이슈 `UNREQUESTED_VALUE_MARKED_AS_USER_INPUT` 반환 |
| 고객/가격 정보 누락 | 요청에 관련 조건이 없거나 missing_fields에 기록 | 고객을 unknown으로 남기고 검증 질문 제시. 가격·원가·수요를 만들지 않음 |
| 요청 조건과 맞지 않는 트렌드 후보 | 후보의 시즌/카테고리/지역/채널이 요청과 불일치 | 해당 후보는 비교 근거로 사용하지 않고 불일치와 확인 질문을 보존 |
| 트렌드와 자사 상품의 같은 속성·같은 값 | 각 값에 Evidence ID가 있고 상품의 주요 조건이 요청과 맞음 | 두 출처에서 값이 관찰됐다고 기록하고, 이를 새 상품 기회로 해석할지는 MD 질문으로 남김 |
| 트렌드와 자사 상품의 같은 속성·다른 값 | 각 값에 Evidence ID가 있음 | 값 차이만 관찰로 기록. 우위, 차별화, 고객 선호라고 단정하지 않음 |
| 자사 상품 속성 자료 없음 | 검색 결과에 해당 속성이 없고 카탈로그 완전성 미정 | 실제 상품에 그 속성이 없다고 표현하지 않고, 비교 불가 제한을 남김 |
| 한 입력 상태가 error/no_results | 해당 결과 payload에 필드가 포함되어 있어도 상태가 실패/결과 없음 | 그 입력의 후보를 생성 근거로 쓰지 않고 상태·제한·확인 질문을 보존 |
| 기획 프롬프트 인젝션 | 사용자 쿼리, trend description 또는 허가 자료 인용문에 역할 변경·Evidence 위조 지시 포함 | 신뢰 지시와 분리된 JSON 데이터로 전달; 출력 request ID와 Evidence ID 검증 통과 없이는 사용하지 않음 |
| 잘못된 구조화 모델 응답 | JSON 오류, 중복 key, 추가 필드, 다른 request ID, 미등록 Evidence ID | 모델 결과를 폐기하고 규칙 기반 초안 fallback과 `TEXT_GENERATION_FALLBACK` 검증 이슈를 반환 |
| Project_07 opaque payload | 합의되지 않은 세부 필드가 포함된 판매·시장 handoff | 모델 프롬프트에는 상태만 전달; 원본 전체 payload는 결과에 보존하고 모델이 해석·재집계하지 않음 |
| 모델 미연결/비활성 | 승인된 텍스트 제공자 없음 또는 기능 비활성 | 규칙 기반 기준선 사용; 외부 텍스트 모델 호출 없음 |
| 입력 데이터 한도 초과 | 직렬화한 기획 입력이 24,000자를 넘음 | T1–T5 결정적 축약 뒤 호출하고 `generation_metadata.prompt_reduction`에 기록; 축약 후에도 넘으면 호출 없이 규칙 기반 fallback(`TEXT_INPUT_OVER_BUDGET`) |

## 기존 결정적 초안 시나리오의 활용

위 시나리오 표는 규칙 기반 generator 및 공통 검증 로직의 회귀 기준으로 유지합니다. LLM 평가에서도 핵심 안전 사례를 재사용하되, 콘셉트의 유용성·구체성에 대한 사람 평가 항목을 더합니다.

## 실행 결과 기록 형식

실험마다 아래 자료를 한 묶음으로 보존합니다.

- 실험 ID, 질문/가설, 비교 트랙(생성 엔진 또는 end-to-end RAG)
- dataset snapshot 및 권한 확인, 개발/holdout 분리
- 코드 commit, prompt version/hash, engine/provider/model/version, 생성 설정
- 입력 컨텍스트와 Evidence ID 목록/순서, 검색 결과 버전
- 원시 모델 출력, 구조 검증 결과, claim-Evidence 검토 레이블 (민감한 원문은 승인된 저장 정책에 따름)
- 지표별 집계와 사례별 결과, MD 블라인드 평가, 평가자 간 일치/불일치
- latency, token/cost 및 실패/재시도(가능한 범위)
- 관찰된 품질 변화, 한계, 다음 실험; 미측정 항목은 명시

모델이 응답에 적은 출처나 Evidence ID 자체는 근거로 인정하지 않습니다. 각 출력 claim의 ID는 입력 Evidence allowlist와 대조하고, 근거가 실제 주장을 지지하는지 평가합니다. 모델 호출 전 자료 전송 권한을 확인하며, API key 및 민감한 원문은 로그나 Git에 남기지 않습니다.

현재 manifest의 구조화 프롬프트 버전은 `new-product-planner-v8-primary-trend`입니다. 입력 데이터의 트렌드는 P06이 규칙으로 고른 기준 트렌드 하나뿐이며(`primary_trend`, `trend_candidates`), 모델은 트렌드를 고르지 않습니다. active `/runs` 경로는 `VOGUE_TEXT_GENERATION_ENABLED=true`일 때만 이 text generator를 선택하고, 기본값에서는 규칙 기반 generator를 사용합니다. 응답의 `generation_metadata`에는 engine/status/prompt version/model 식별자가 포함되며 프롬프트나 모델 원문은 포함되지 않습니다. 실행 기록을 별도 저장하지 않습니다. 합성 mock 테스트는 파싱·요청 격리·Evidence allowlist·fallback을 검증합니다. 별도 OpenAI Responses API 어댑터는 도구를 비활성화하고 `store=false`를 지정합니다. provider 실패나 구조화 응답 검증 실패 시 HTTP 경로도 규칙 기반 초안으로 fallback합니다. 실 API 호출 1회의 성공은 프롬프트 품질이나 프롬프트 인젝션 저항성을 입증하지 않으며, 계속적인 합성 평가와 MD 검토가 필요합니다.
