# MD 기획 업무 적합성 검토 및 평가 제안

- 기준일: 2026-11-10
- 상태: 저장소 기반 초기 검토 · MD 업무 검증 전 · 제안
- 범위: Project_06 내부 초안 생성과 Project_08에 전달할 검토 데이터
- 입력 자료: 현재 코드·설계 문서·`data/interim/cross-agent-demo-27ss-planning-draft.md` 및 합성 평가 시나리오

## 요약

현재 구현은 **근거 출처와 입력 상태를 보존하고, 불확실한 내용을 사실처럼 말하지 않는 안전한 기초**를 갖췄습니다. 다만 실제 MD 기획 업무에 최적화됐다고 결론 내릴 수는 없습니다. 운영 upstream·승인된 내부 기획 자료·실제 MD 평가가 없으며 기본 생성기는 규칙 기반입니다. 현재 결과는 입력을 정리하고 검토 질문을 나열하는 데 유용하지만, MD가 여러 기획 방향을 비교하고 다음 결정을 내리는 문서 구조는 충분히 검증되지 않았습니다.

여기서 말하는 “업무 적합성 부족”은 상품기획 지식의 부재를 뜻하지 않습니다. 현재 증거로는 **실무 적합성을 확인할 평가가 완료되지 않았고**, 합성 예시에서 선택지·trade-off·결정 요청이 구조화되어 있지 않다는 의미입니다.

## 확인된 현황

| 영역 | 확인 결과 | 업무 적합성 영향 |
| --- | --- | --- |

| 기본 생성 | 운영 API 기본 경로는 결정적 규칙 기반 생성기. 텍스트 모델 제공자 미연결 | 반복 가능하지만 MD가 원하는 합성·비교·서술 품질은 실무 평가가 없음 |
| 내부 결과 모델 | `ProductConceptDraft`는 단일 `product_definition`, 속성, 관계, 차별화, 위험, 질문 중심 | 대안별 차이와 선택 이유를 표현하는 전용 구조가 제한적 |
| 근거·안전 | claim 종류, Evidence allowlist, 입력 상태·제한 보존과 프롬프트 경계가 있음 | 강점. 다만 유효한 Evidence ID가 해당 문장의 의미까지 지지하는지는 별도 사람 평가 필요 |
| 시장/사업 판단 | 판매·시장 결과를 Project_07의 opaque handoff로 보존. 재고를 수요로 해석하지 않음 | 적절한 책임 분리. 초안은 해당 분석의 범위·제한을 MD 판단과 연결하는 방법이 미정 |
| 검토 경험 | Project_08이 UI를 소유하고 Project_06은 구조화 결과 제공 | 화면 순서·비교 방식·검토 상태는 Project_08 및 MD 협의 필요 |
| 평가 근거 | 현재 데모와 관련 fixture는 합성. MD 블라인드 평가 결과 없음 | 품질 또는 생산성 향상을 주장할 수 없음 |

## 데모 초안에서 확인한 업무상 공백

교차 에이전트 데모는 합성 자료임을 표시하고 입력 상태와 제한을 공개합니다. 다음 부분은 MD 검토를 더 쉽게 만들 수 있도록 구조화할 후보입니다.

1. **기회 제안이 하나의 요약 문장에 머뭅니다.** 데모는 트렌드명과 비교 대상 수를 요약하지만, 그 입력에서 어떤 상품 방향을 검토할지 대안으로 구분하지 않습니다.
2. **대안 간 차이와 trade-off가 없습니다.** 색상·소재·핏 등 속성은 나열되지만, 서로 다른 콘셉트 방향의 차이, 각 방향의 근거, 미확정 가정이 비교 가능한 단위로 묶여 있지 않습니다.
3. **질문은 있지만 결정 맥락이 약합니다.** 가격대·생산 가능성·대상 고객 확인 등이 질문으로 나오지만, 무엇을 먼저 결정해야 하는지, 답변 주체가 누구인지, 답변이 어떤 기획 선택을 바꾸는지는 명확하지 않습니다.
4. **시장 결과는 보존되지만 제안으로 이어지는 경로가 제한적입니다.** 데모의 시장 finding은 합성·부분 표본으로 정확히 한정되어 있습니다. 이 결과만으로 고객 선호·수요·매출 전망을 만들 수 없으므로, MD가 조사 범위·추가 확인 필요성을 판단할 표시가 필요합니다.
5. **다음 단계에 필요한 최소 정보가 합의되지 않았습니다.** 필수 검토 항목과 보류/추가 확인 조건은 담당자 합의 없이 구현하면 안 됩니다.

위는 단일 합성 데모에 대한 관찰이지 전체 요청군에서의 빈도·영향 측정은 아닙니다.

## 출력 구조 개선 제안

기존 내부 모델 및 Project_08 소비처의 호환성을 먼저 확인하고, 아래와 같은 **내부 검토 view**를 제안합니다. 이는 공용 wire schema나 승인된 필수 필드가 아닙니다.

- **요청 및 입력 상태:** request 범위, 각 producer 상태, schema/source, 기간·단위·기준 시점, 입력 제한
- **기획 검토 목적:** 사용자가 요청한 목표와 입력만으로 판단 가능한 범위
- **콘셉트 대안:** 합의된 업무 필요가 있을 때만 제안. 각 대안에 이름, 상품 방향, 달라지는 속성, 속성별 claim 종류·Evidence, 제안 근거, 가정, 리스크, 비교 불가 항목을 묶음
- **비교 요약:** 동일한 입력 조건에서 대안 간 실제 차이만 표시. 가중치나 종합 순위는 승인된 기준이 없으면 산출하지 않음
- **기존 상품 관계:** 관찰된 일치/차이와 데이터 커버리지 한계를 분리. 시장 공백·선호 결론으로 승격하지 않음
- **Project_07 handoff:** 상태와 원본 참조, 범위·기간·단위·제한을 보존. Project_06은 지표를 재집계하지 않음
- **MD 결정 항목:** 결정/확인 질문, 질문 이유, 필요한 정보, 담당 역할 제안, 답변에 따라 바뀌는 기획 항목. 역할은 합의 전 TBD
- **미판단 항목:** 가격·원가·마진·생산 가능성·발주량·최종 채택 등 이 초안에서 결론 내리지 않는 항목

대안 개수와 결정 단계는 MD가 업무 흐름을 확인한 후 정합니다. 대안을 만들 근거가 부족하면 억지로 차이를 만들지 않고 한 방향 또는 비교 보류로 표현합니다. API 필드 추가·변경은 소비처와 호환성 합의 후에만 합니다.

## 합성 평가 루브릭 제안

담당자 합의 전에는 각 차원을 사례별로 관찰하고 종합 점수·가중치·통과선을 만들지 않습니다.

| 평가 차원 | 평가자가 확인할 점 | 자동 확인 가능성 |
| --- | --- | --- |
| 기획 제안의 명료성 | 제안과 사실 관찰이 구분되고, MD가 제안 방향을 한눈에 이해하는가? | 부분적 |
| 근거 연결 | Evidence가 실제 주장을 뒷받침하고 출처·범위가 맞는가? | ID는 자동, 의미 지지는 사람 검토 |
| 대안 비교 가능성 | 필요한 경우 대안 간 차이가 실질적이고 동일 기준에서 비교되는가? | 일부 구조 검사 + MD 평가 |
| 업무 실행 가능성 | 다음 검토 단계에서 무엇을 확인·수정할지 알 수 있는가? | 주로 MD 평가 |
| 제약 준수 | 요청 조건과 금지 경계가 지켜지는가? | 필드·enum 일부 자동 |
| 불확실성 처리 | 누락·충돌·부분 상태가 올바르게 나타나고 질문으로 이어지는가? | 상태/누락 자동, 적절성은 MD 평가 |
| 과장 방지 | 재고→수요, 표본→시장 전체, 관찰→선호/전망으로 바뀌지 않았는가? | 일부 규칙 + 사람 검토 |
| 읽기·검토 부담 | 초안을 이해하고 검토하는 데 걸리는 시간과 재작업이 줄었는가? | MD 사용성 평가 및 기준선 필요 |

## 합성 사례 목록

실제 자료 없이 다음 사례를 고정하고, 현재 결과와 제안 내부 view를 나란히 검토합니다. 사례 정의 파일은 [`md-planning-evaluation/cases.json`](../../examples/fixtures/md-planning-evaluation/cases.json)에 있습니다.

| 사례 | 입력 조건 | 검토 초점 |
| --- | --- | --- |
| 충분한 합성 근거 | 요청·트렌드·재고 모두 `ok`, 유효 Evidence | 근거와 제안 분리, 비교 가능한 대안이 실제로 필요한지 |
| 부분 입력 | Trend 또는 stock `partial` | 제한이 관련 주장·질문에 연결되는지 |
| 결과 없음 vs 실제 0 | upstream `no_results`와 별도 fixture 내 명시 수량 0 | 두 상태가 구분되는지 |
| Project_07 오류 | 판매/시장 `error`, 나머지 유효 | 실패 결과를 근거로 쓰지 않고 제한된 초안으로 표시하는지 |
| 요청 충돌 | 요청 속성과 Trend 또는 재고 값 충돌 | 충돌을 선택지/질문으로 정직하게 표현하는지 |
| 고객/가격/생산 정보 누락 | 필드 누락 또는 unknown | 타깃·가격·생산 가능성을 만들어내지 않는지 |
| 근거 없는 속성 | 속성 값은 있으나 Evidence ID 없음 | 사실 관찰로 표현하지 않는지 |
| Evidence 참조 오류 | 등록되지 않은 Evidence ID | 검증에서 거부/검토 상태가 되는지 |
| 복수 방향 비교 | 같은 요청에 서로 다른 합성 속성 근거가 전달됨 | 차이가 근거/제안/가설 중 무엇인지, 실제 대안 필요 여부 |

## 평가 절차와 한계

1. 담당자 질문에 답을 받아 업무 단계·대안 필요 조건·검토 필수 항목·담당 역할을 합의합니다.
2. 합의된 루브릭과 사례를 고정하고, prompt 개발 사례와 holdout 평가 사례를 분리합니다.
3. 가능한 경우 출력의 시스템/엔진 이름을 가리고 MD 평가를 수행합니다. 평가자는 근거 적합성·수정 필요성·검토 시간·다음 단계 명확성을 사례별로 기록합니다.
4. 사람 평가와 자동 검증을 별도 보고하고, 사례 수와 평가자 불일치도 공개합니다.
5. 실제 평가 전에는 MD 생산성·기획 품질·시장 성과가 개선됐다고 주장하지 않습니다. 합성 사례는 파이프라인과 안전성 점검에만 사용합니다.

현재 MD 담당자 응답과 실사용 평가는 제공되지 않았습니다. 이 문서는 실제 워크플로우의 완전한 요구사항 문서가 아니라 검토를 시작하기 위한 저장소 기반 제안입니다.
