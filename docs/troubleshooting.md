# 트러블슈팅과 교훈

novelty 서비스를 만들면서 겪은 문제를 짧은 사후 검토 형식으로 정리했다. 항목마다 증상, 원인(근거), 해결, 검증, 교훈, 해결 커밋을 적는다.

커밋 링크는 이 저장소의 히스토리를 가리킨다. 수치는 개발 중 기록한 실행이나 그 기록을 오프라인으로 다시 돌린 결과에서 가져왔다. 어느 항목도 검증에 유료 API 호출이 필요하지 않다.

| ID | 영역 | 증상 |
|---|---|---|
| [T-HTTP-01](#t-http-01) | HTTP | 큰 요청이 `413` 대신 broken pipe로 끝남 |
| [T-TEXT-01](#t-text-01) | 텍스트 LLM | 유료 호출 뒤 인용한 근거 ID가 모두 거부됨 |

| [T-IMG-02](#t-img-02) | 이미지 | 착장 이미지가 기존 재고를 반영하지 않음 |

## T-HTTP-01 · 큰 요청이 `413` 대신 broken pipe로 끝남

orchestrator 저장소와 함께 쓰는 항목이다. 이 문서는 서비스 쪽을 다루고, 시스템 쪽 해결은 orchestrator 문서에 있다.

- **증상**
  - orchestrator가 novelty를 호출하는 중 본문을 보내다가 `BrokenPipeError`가 났다.
  - orchestrator는 이를 `503 UPSTREAM_UNAVAILABLE`로 보고했고, 서비스 로그에는 요청이 남지 않았다.
  - 처음 실패한 요청의 본문은 1,041,802바이트였다.
- **원인**
  - 서비스는 본문을 `MAX_RUN_BODY_BYTES = 1_000_000`바이트까지만 받는다(`src/fashion_planner_novelty/server/app.py`).
  - `Content-Length`가 이보다 크면 핸들러는 본문을 읽지 않고 `413 PAYLOAD_TOO_LARGE`를 보낸다.
  - 핸들러는 HTTP/1.0으로 동작해서 응답 직후 연결을 닫는다.
  - 아직 본문을 쓰던 클라이언트는 응답을 읽기 전에 닫힌 소켓에 부딪힌다. 그래서 `413` 대신 broken pipe나 connection reset을 본다.
  - 큰 본문의 대부분은 이 서비스가 읽지 않는 trend·inventory 결과의 필드였다.
- **해결**
  - 서비스 쪽: 한도는 그대로 둔다. 단일 프로세스 서버를 무제한 본문에서 보호하는 장치다.
  - 시스템 쪽: orchestrator가 상위 결과에서 이 서비스가 읽지 않는 필드를 뺀 등록 투영(projection)을 보낸다. 기록된 요청은 604,993바이트에서 176,069바이트로 줄었고, 착장 이미지용 재고 사진을 넣은 뒤에는 292,493바이트였다. 자세한 내용은 orchestrator의 트러블슈팅 문서를 본다.
- **검증**
  - 외부 네트워크 없이 루프백에서 실제 핸들러로 재현했다.
  - 1,041,802바이트 본문은 131,072바이트를 보낸 시점에 `BrokenPipeError`로 끝났고 `413` 응답은 끝내 읽지 못했다.
  - 4,000,000바이트 본문은 `ConnectionResetError`로 끝났다.
  - 끊기는 위치는 소켓 버퍼 크기에 따라 다르다.
  - `tests/test_http_gate.py`는 한도를 넘는 `Content-Length`에 본문을 읽기 전 `413`을 보내는지 확인한다.
- **교훈**
  - 조기 오류 응답은 클라이언트가 읽을 수 있을 때만 쓸모가 있다. 서버가 본문을 읽기 전에 요청을 거절하면 클라이언트는 연결 재설정만 볼 수 있다.
  - 한도를 API 문서에 적고, 보내는 쪽에서 크기를 먼저 확인한다. 업로드 중 재설정은 "서비스 다운"이 아니라 "너무 클 수 있음"으로 다룬다.
- **커밋**: 한도 도입은 {{commit:ee02ebf}}. 투영 해결은 orchestrator 저장소에 있다.

## T-TEXT-01 · 유료 호출 뒤 인용한 근거 ID가 모두 거부됨

- **증상**
  - 텍스트 모델은 응답했지만, 검증이 모델이 인용한 근거 ID를 전부 거부했다.
  - 실행은 `TEXT_OUTPUT_INVALID`로 규칙 기반 Draft로 대체됐다.
  - 기록된 실행 두 건에서 허용된 ID는 177개 중 0개였다.
- **원인**
  - `serialize_untrusted_prompt_data`(`domain/prompt_safety.py`)는 `PROMPT_DATA_MAX_CHARS`(24,000자)를 넘는 기획 데이터를 6,000자 미리보기로 바꾼다.
  - 미리보기에는 읽을 수 있는 근거 ID가 없어서 응답이 인용해도 되는 ID 집합이 비었다.
  - 기록된 입력은 25,022~26,756자였다.
- **해결**: `domain/prompt_budget.py`가 상한을 넘는 데이터를 모델 호출 없이 결정적으로 줄인다. 한 단계씩 적용하고 단계마다 직렬화한 크기를 다시 잰다.
  1. T1: 트렌드·재고 목록에 이미 있는 한계 문장을 뺀다.
  2. T2: 참조 토큰과 숫자만 다른 문장을 묶는다.
  3. T3: 구조를 압축한다.
  4. T4: 근거 ID를 짧은 별칭(`E1`…`En`)으로 바꾸고, 응답에서 원래 ID로 되돌린다.
  5. T5: 내용을 줄인다(손실 있음).

  T5 뒤에도 넘으면 모델을 호출하지 않고 `TEXT_INPUT_OVER_BUDGET`으로 규칙 기반 Draft를 쓴다. 축약한 실행은 `generation_metadata.prompt_reduction`에 그 내용을 기록한다.
- **검증**
  - 기록된 요청을 오프라인으로 다시 돌렸다. T1만으로 25,023자가 22,887자로 줄었고 ID 177개가 모두 허용됐다.
  - 상한 아래 요청은 바이트 단위로 같은 프롬프트를 만들었다.
  - 테스트: `tests/test_prompt_budget.py`
- **교훈**: 데이터 모양을 조용히 바꾸는 안전 상한은 결과를 검증하는 쪽에도 보여야 한다. 원본 객체가 아니라 실제로 보내는 형태를 잰다.
- **커밋**: {{commit:26454ed}}

## T-TEXT-02 · 축약한 프롬프트에서 모델 문장이 바뀌거나 값이 비는 일이 생김

- **증상**: 축약한 실행에서만 두 가지 실패가 나타났다.
  - 별칭처럼 생긴 토큰(예: 트렌드 설명 속 `E2`)이 실제 근거 ID로 바뀌었다.
  - 묶은 문장을 그대로 옮긴 값이 비어 `EMPTY_CLAIM_VALUE`로 대체됐다.
- **원인**
  - T4는 실제 근거 ID만 보고 별칭 접두를 골랐다. 그런데 복원 단계는 응답 전체에서 별칭 모양의 토큰을 바꾼다.
  - T2 복원은 노트만 지우지 않고 묶음 노트가 붙은 줄 전체를 지웠다.
- **해결**
  - 별칭 접두가 데이터 안의 모든 별칭 모양 토큰을 피한다.
  - 묶은 줄을 복원할 때 노트만 지운다.
- **검증**: 기록된 요청 결과가 이전과 같았다. 상한 아래 14건은 바이트 단위로 같았고, 축약한 3건의 허용 ID는 177, 177, 179개였다.
- **교훈**: 모델 앞에 두는 되돌릴 수 있는 인코딩은 직접 만든 필드뿐 아니라 모델이 쓴 자유 문장에서도 되돌릴 수 있어야 한다.
- **커밋**: {{commit:3abae2c}}

## T-IMG-01 · 디자인 디테일이 이미지 프롬프트에 들어가지 않음. 두 이미지가 서로 다른 옷을 보여 줌

- **증상**
  - 프린지나 도트 같은 디테일이 Draft에는 있는데 생성된 이미지에는 없었다.
  - 상품 이미지와 착장 이미지가 눈에 띄게 다른 옷(예: 칼라 모양이 다름)을 보여 줬다.
- **원인**
  - Draft는 `dataclasses.asdict`로 만든다. 이때 `ProductProfile.details`가 tuple로 남는데, `_image_profile_from_draft`는 list만 받았다. 그래서 모든 이미지 사양에서 `details`가 빠졌다.
  - 응답은 정상으로 보였다. 나중의 JSON 왕복에서 tuple이 list로 바뀌기 때문이다.
  - 근거: 기록된 이미지 실행 16건 모두 `product_specification_sha256`이 details를 *뺀* 프로필의 해시와 같았다.
  - 별도로, 두 이미지는 텍스트 사양만 공유하는 독립 동시 호출이었다.
- **해결**
  - list와 tuple을 모두 받는다.
  - 상품 이미지를 먼저 만들고, 착장은 저장된 상품 이미지를 입력으로 하는 Images edits 호출로 만든다. 그래서 두 이미지가 같은 옷을 보여 준다.
  - 상품 이미지가 없으면 착장을 텍스트만으로 그리지 않고 `OUTFIT_REFERENCE_UNAVAILABLE`로 건너뛴다.
- **검증**: `tests/test_handoff_runs.py`의 `test_image_profile_keeps_details_of_an_asdict_draft`와 `test_outfit_is_an_edit_of_the_stored_product_image_and_never_overlaps_it`. 두 번째 테스트는 편집 호출이 상품 호출이 끝난 뒤에야 시작하는지도 확인한다.
- **교훈**: 직렬화 왕복이 타입 버그를 숨길 수 있다. 출력은 맞아 보였고 내부 호출만 틀렸다. 투영은 직렬화 전, 실제로 넘기는 객체로 테스트한다.
- **커밋**: {{commit:d05e74e}}

## T-IMG-02 · 착장 이미지가 기존 재고를 반영하지 않음

- **증상**: 착장 이미지가 신상품만 보여 줬다. 반면 기획서는 트렌드마다 기존 재고 상품을 함께 보여 줬다.
- **원인**: 예전 재고 착장 경로를 의도적으로 지운 뒤({{commit:2addab0}}) 착장 호출에 재고 상품을 넘기는 코드가 없었다.
- **해결**
  - `domain/outfit_companion.py`가 규칙(`primary_trend_stock_slot`)으로 재고 상품 하나를 고른다. 주 트렌드의 재고 중 순위가 가장 높고, 신상품과 착장 역할이 겹치지 않는 상품이다.
  - 재고 결과에 그 상품 사진이 있으면 편집 호출의 두 번째 입력 이미지로 넣는다.
  - 카테고리·색·소재·핏은 JSON으로 프롬프트에 넣는다.
- **검증**: `tests/test_outfit_companion.py`. 착장 visual의 `companion`에 고른 상품이 기록되고, 고르지 못하면 `null`이다.
- **교훈**: 두 화면이 "같은 기획"을 보여 준다면 같은 선택 규칙을 쓰고, 무엇을 골랐는지 기록한다.
- **커밋**: {{commit:5f280b8}}

## T-PLAN-01 · Draft 하나가 여러 트렌드의 속성을 섞음

- **증상**: 드레스 기획에서 패턴은 한 트렌드(폴카 도트)에서 가져왔는데, 기획서는 다른 트렌드를 보여 줬다.
- **원인**: 규칙 생성기가 쓸 수 있는 트렌드를 모두 나열하고 그 속성을 한 프로필에 합쳤다.
- **해결**
  - `domain/trend_basis.py`가 주 트렌드 하나를 고른다. 근거가 연결된 디자인 속성이 가장 많은 것, 같으면 근거 ID가 많은 것, 그래도 같으면 먼저 입력된 것이다.
  - 규칙 기반 Draft와 텍스트 LLM 입력은 그 트렌드만 쓴다.
  - `draft.trend_basis`에 선택을 기록한다.
- **검증**
  - 기록된 요청 20건을 오프라인으로 다시 돌렸다. 규칙이 기대한 트렌드를 고른 경우가 20/20, 프로필 속성이 그 트렌드에서만 온 경우가 20/20이었다.
  - 가장 큰 LLM 입력이 26,756자에서 16,795자로 줄어, 축약이 필요한 기록 요청이 더는 없었다.
  - 테스트: `tests/test_trend_basis.py`
- **교훈**: "근거를 모두 쓴다"는 설계가 아니다. 결과가 *무엇에 관한* 것인지 정하고, 그 결정을 출력에 기록해 소비자가 기댈 수 있게 한다.
- **커밋**: {{commit:25a4ff3}}

## T-PLAN-02 · 색이 여러 개인 트렌드에서 상품 색이 비어 있음

- **증상**: 주 트렌드에 근거가 연결된 색이 둘 이상이면 프로필 색이 비어서 이미지에 트렌드 색이 없었다.
- **원인**: "값이 하나일 때만 올린다"는 규칙이 소재·실루엣뿐 아니라 색에도 적용됐다.
- **해결**
  - 색은 입력 순서상 첫 번째로 근거가 연결된 색을 쓴다. 사용자가 요청한 색이 있으면 그것이 우선이다.
  - 텍스트 LLM 경로도 빈 칸 채우기 뒤에 같은 규칙을 적용한다.
- **검증**: `tests/test_trend_basis.py`의 `FirstEvidenceColourTests`
- **교훈**: 보수적인 규칙은 다음 단계를 굶길 수 있다. Draft가 방어 가능한지만 보지 말고, 이미지 프롬프트가 실제로 무엇을 받는지 확인한다.
- **커밋**: {{commit:dbcd63b}}

<a id="t-plan-03"></a>
## T-PLAN-03 · 프로필 변경이 실패하는 테스트와 함께 병합됨

- **증상**: 이번 공개의 기준 커밋에서 단위 테스트 173개 중 15개가 실패했다. 바로 앞 병합에서는 모두 통과했다.
- **원인**
  - 늦게 들어간 두 변경이 동작을 바꾸면서 테스트를 고치지 않았다.
    - 규칙 기반 Draft의 빈 프로필 칸을 표시된 검토 제안값으로 채운다({{commit:96fc1a6}}).
    - 텍스트 모델이 category, product_type, gender, season, material을 반드시 채워야 한다({{commit:0597005}}).
  - 14건은 오래된 테스트 픽스처와 기대값 때문이었다.
  - 1건은 실제 회귀였다. `generation_metadata.llm_empty_fields`에 보고하는 필드 목록이 더는 빌 수 없는 필드로 좁혀져서, 색·실루엣을 채운 사실이 보고되지 않았다.
- **해결**
  - 테스트를 현행 동작에 맞췄다. 가짜 모델 응답에 필수 필드를 채우고, 기대값에 제안값을 넣었다.
  - 자유 문장 대신 명시적 요청 속성으로 "명시값이 제안값보다 우선"을 검증하게 했다.
  - 보고 대상을 프로필 7개 필드 전체로 되돌렸다.
- **검증**: 테스트를 고친 뒤 기준 커밋의 173개가 모두 통과했다. 이후 운영 경로에서 쓰지 않는 코드와 그 테스트를 정리하고 관문 테스트를 더해 현재 145개이며, 네트워크를 막은 실행기에서 모두 통과한다.
- **교훈**: CI가 없으면 "테스트 통과"는 아무도 확인하지 않은 주장이다. 이 저장소는 이제 push와 pull request마다 오프라인 테스트를 돌린다.
- **커밋**: {{commit:96fc1a6}}, {{commit:0597005}}

<a id="t-status-01"></a>
## T-STATUS-01 · 실데이터 실행이 모두 `partial`로 보고됨

- **증상**: Draft와 이미지 두 장을 모두 만든 실행도 `partial`로 보고됐고, orchestrator는 그 상태를 기획 전체로 넘겼다.
- **원인**: 상위 입력의 한계 문장 하나만 있어도 분석이 `partial`이 됐다. 예: 샘플 재고, 대체한 지난 시즌, 아직 정하지 않은 성별 정책.
- **해결**
  - 상태는 산출물을 기준으로 한다. Draft와 이미지 두 장이 만들어지고 상위 입력이 모두 `ok`이면 `ok`, 아니면 `partial`이다.
  - 한계와 검증 이슈는 그대로 모두 돌려준다.
- **검증**: `tests/test_handoff_runs.py`의 `test_complete_deliverables_with_informational_limitations_are_ok`
- **교훈**: 상태 필드는 질문 하나에만 답해야 한다. 세부 사항은 상태에 접어 넣지 말고 이슈 목록에 둔다.
- **커밋**: {{commit:46555a2}}

## T-OPS-01 · 컨테이너가 시작하자마자 종료됨

- **증상**: 컨테이너가 `Prompt manifest is unavailable or invalid`를 내고 바로 멈췄다.
- **원인**: 프롬프트 레지스트리는 import할 때 `prompts/manifest.json`을 읽는데, Dockerfile이 `prompts/`를 이미지에 복사하지 않았다.
- **해결**: Dockerfile에 `COPY prompts/ ./prompts/`를 넣었다.
- **검증**: 컨테이너가 시작하고 `GET /api/health`가 `200`을 돌려준다.
- **교훈**: import 시점에 읽는 파일은 런타임 이미지의 일부다. 서버 모듈을 import하는 컨테이너 스모크 테스트를 돌린다.
- **커밋**: {{commit:8c78c82}}

<a id="t-test-01"></a>
## T-TEST-01 · 오프라인 테스트가 가짜 키로 실제 API에 접속함

- **증상**: 단위 테스트 하나가 자리표시자 키로 실제 텍스트 API에 요청을 보냈다.
- **원인**: 텍스트 생성은 기본으로 켜져 있고 API 키가 있으면 만들어진다. 테스트는 이미지 provider만 바꿔치기하고 HTTP 클라이언트는 그대로 둬서, 텍스트 경로가 실제 엔드포인트를 불렀다.
- **해결**
  - 테스트가 `urllib.request.urlopen`을 바꿔치기한다.
  - 공개판의 테스트 실행기는 루프백이 아닌 연결을 모두 막고, 시도가 있으면 실패한다(README의 '테스트' 절 참고).
- **검증**: 가짜 키와 이미지 생성을 켠 채 전체 테스트를 돌려 외부 연결 시도 0건을 확인했다.
- **교훈**: "오프라인"은 가정하지 말고 강제해야 한다. 외부 연결을 실패로 만드는 가드가 예상 못 한 청구서 한 장보다 싸다.
- **커밋**: {{commit:d05e74e}}
